# 桌面音频采集工具：需求整合与开发方案

> 文档性质：用于项目立项、原型和 MVP 开发的建议基线。  
> 上游的《需求分析文档》是讨论材料，本方案会保留其核心意图，但不把其中的界面、参数和技术建议视为已决策需求。  
> 已确认技术路线：Electron + React + TypeScript + Rust 独立音频引擎。  
> 编制日期：2026-08-10

## 1. 结论摘要

建议将产品定位为一款 **Windows 优先、本地优先、面向大批量朗读型语音数据生产的桌面工作台**，而不是普通录音机，也不是移动端 App 的等比例移植。

建议的主线是：

1. 一次作业对应一个 Session，Session 内保持连续音频时轴。
2. 句子不直接等于一个录音文件，而是指向时轴上某段样本区间的索引。
3. 重录不修改或截断已录音频，而是在时轴尾部追加新 attempt，并切换有效版本。
4. 时间定位使用整数样本位置，不用系统时钟浮点秒做真值。
5. 录音引擎、业务状态、文件持久化和 UI 解耦；音频回调不做写盘、JSON 序列化或复杂 UI 工作。
6. 采用移动端已验证的 UX 模式，但不直接继承其“每句一个文件、录完立即上传并机检”的数据链路。
7. Electron/React 只负责界面和桌面应用交互；Rust sidecar 是录音、样本时轴、Session 日志、恢复和导出的权威实现。

首版 MVP 建议聚焦在：脚本导入、设备预检、稳定连续录音、逐句打点、确认/重录/跳过、崩溃恢复、回放和一键导出。登录、任务领取、团队、OSS 上传、声纹和服务端机检默认不进入本地 MVP，除非业务明确要求桌面端接入现有平台。

### 1.1 当前落地状态（2026-08-10）

本轮已完成可运行基线：

- Rust 通过 CPAL 枚举系统输入端点；Windows 对应 WASAPI，可选择外置声卡设备、采样率和具体输入通道。
- 采集回调支持驱动常见的整数与浮点样本格式，并优先选择高精度兼容格式；内部统一为 `f32` 后再写入交付格式。
- 实际支持 `16-bit PCM`、`24-bit PCM` 和 `32-bit Float` WAV；母带、试听切片和最终单句导出保持同一编码，受控试运行默认 `48 kHz / 16-bit PCM / Mono`。
- React 设置页显示设备能力矩阵、可用采样率、当前采样率下的输入通道和驱动样本格式；不支持的组合不会进入录制。
- 停止录制会先暂停输入并等待回调稳定，再确认样本全部写盘，避免停止瞬间的捕获数与写盘数不一致。
- 已通过三种位深的写入/切片测试、类型检查、Rust Clippy、release 构建、目录打包和本机真实麦克风 24-bit 实录验证。

Windows 落地仍需执行硬件验收矩阵：Windows 10/11 各至少一台，覆盖内置麦克风、USB 麦克风和目标客户常用外置声卡；每种设备验证 48/96 kHz、输入 1/2、16/24/32-bit、2 小时长录、拔插和磁盘异常。当前基线不直接绑定 ASIO SDK；仅提供 ASIO 端点的设备需另立兼容项，常规能出现在 Windows 输入设备中的声卡走 WASAPI。

## 2. 材料解读

### 2.1 讨论文档的核心意图

《需求分析文档》最有价值的不是其示意界面，而是以下原则：

- 连续母音频与文本标注解耦。
- 以 `start_sample` / `end_sample` 建立精确可重算的时间索引。
- 重录是不可变尝试记录，而不是覆盖原音频。
- 自动保存和崩溃恢复是核心能力，不是后期优化。
- 最终导出单句 WAV 和结构化元数据，以对接 ASR 训练、质检或交付流程。
- 高频录制场景应尽量脱离鼠标，支持快捷键和明确的录制状态。

以下内容应视为“可讨论建议”，而不是已锁定要求：

- 讨论稿曾建议默认 `48 kHz / 24 bit / Mono`；当前受控试运行已明确采用 `48 kHz / 16 bit / Mono`，正式项目仍应由任务规范和设备能力共同决定。
- 所有会话严格只保存一个物理 WAV；为恢复和超大文件安全，实现上更适合保持“逻辑连续”，底层容许无缝分段。
- 开始前和结束后必须用倒计时强制录制固定静音；桌面版可将静音时长主要作为导出边界扩展参数，强制倒计作为可选任务策略。
- 讨论文档提到的 PySide6 路线不再作为本项目实现基线；已改为 Electron + React + Rust sidecar，但仍必须通过真机尖刺验证长录音、设备热插拔、24-bit 写盘和安装包行为。

### 2.2 移动端可借鉴的 UX

参考工程包含 Android 1.4.4.0、iOS 1.4.20 和一个以 Android 为基线的 React Native 重写项目。React Native 项目的音频流程已经很完整，但从其 ROADMAP 可看出仍属待真机验收状态，因此它适合做 UX 和业务流程索引，不应单独作为稳定性依据。

桌面版建议借鉴：

- **任务目录**：“待完成 / 已完成 / 待重录 / 已跳过”分类，可快速回到任意已录句复核。
- **单任务主界面**：顶部显示总进度；中间用大文本卡展示当前句；下方固定波形、计时和主操作区。
- **朗读要求标签**：如“慢语速”“无杂音”“情绪”等应作为文本上方的短标签，不埋在说明段落中。
- **录前检查**：麦克风权限、设备是否有信号、环境噪声、峰值/削波等在正式作业前给出明确通过/不通过结果。
- **顺序保护**：新句默认按顺序推进，录音或文件处理中不允许切换；已录句仍可自由回看。桌面版应让“严格顺序”成为可配置任务策略。
- **操作状态可见**：录音、结束收尾、写盘、校验、导出、失败重试都应有不同状态，避免用户重复点击。
- **录后快速处理**：试听、确认、重录、下一条是一级操作；重录原因或驳回标签可作为辅助信息。
- **中断和阻断提示**：设备断开、任务不可用、文件上传/校验失败时，明确告诉用户数据是否仍保存在本地及下一步怎么做。
- **长录音打点模式**：移动端的连续录音和打点能力可作为桌面版的高级模式，但不和普通逐句采集混在一个编辑器状态中。

不建议直接搬到桌面 MVP 的移动端能力：

- 账号登录、团队和任务领取。
- 每句录完立即 OSS 上传、服务端检测并才能进入下一句。
- 声纹注册、年龄/性别分类、服务端 ASR/VAD/SNR 拦截。
- 面向手机的卡片滑动手势、锁屏/来电处理和后台录音交互。

## 3. 产品目标与用户

### 3.1 核心用户

- 在固定工位上使用 USB 麦克风、外置声卡或专业音频设备的语音采集员。
- 负责导入文本、开始作业、处理读错/跳过并导出交付包的项目操作员。
- 使用导出单句 WAV 和元数据做二次质检、标注或建模的数据工程师。

### 3.2 成功指标

- 完成一条合格文本的常用操作不超过一个主按键动作，重录不超过两个按键动作。
- 正常退出、断电或崩溃后，已确认的句子和其音频索引可恢复。
- 连续录制 2 小时无已知丢帧、音频断裂、UI 卡死或时间索引偏移。
- 导出的每个 WAV 都能通过元数据追溯到 Session、文本 ID 和选中的 attempt。
- 重复导出同一 Session 产生一致的边界和文件命名（除非用户改变导出配置）。

## 4. 范围与优先级

### 4.1 P0：MVP 必须完成

#### A. 项目与脚本

- 新建、打开、继续和安全关闭 Session。
- 导入 UTF-8/UTF-8 BOM 的 TSV 或 CSV，最少包含 `id` 和 `text`，`label` 可选。
- 导入前预览列映射，检查缺列、重复 ID、空文本、未知编码和行号。
- 导入后固定一份脚本快照，防止外部原文件改变导致时间索引错位。

#### B. 设备与录音配置

- 列出当前输入设备，显示友好名称、Host API、通道数和默认参数。
- 支持配置采样率、位深、声道和目标通道映射；不支持的组合应在开始前失败，不得静默降级。
- 开始前必须完成 5–10 秒设备预检：有信号、RMS/峰值可见、无连续削波、默音不异常。
- 保存本机设备配置预设，但每个 Session 都固化实际使用的参数。

#### C. 录音与逐句操作

- 进入作业后建立一条逻辑连续的样本时轴。
- 当前句支持“开始一次尝试”和“结束一次尝试”，边界从音频引擎样本计数器获取。
- 结束后支持试听、确认、重录和跳过；重录保留历史 attempt。
- 可返回已录句并从多个 attempt 中更换选中版本。
- 提供输入电平、峰值、剪切警告、Session 时长、当前 attempt 时长、已完成/待录/待重录数。
- 设备丢失、队列溢出、写盘失败或磁盘空间不足时立即进入故障状态，禁止继续标记数据为有效。

#### D. 保存与恢复

- 样本流持续写入封闭可恢复的音频分段，不依赖结束会话时才生成完整文件。
- 所有业务变更追加到事件日志；每次结束/确认/重录/跳过后原子更新快照。
- 程序启动时扫描未正常关闭 Session，先运行一致性检查，再让用户继续、另存或封存。
- 最小恢复承诺：已封闭音频分段不丢失；业务索引最多回退到最近一次原子快照；当前未封闭分段尽力修复。

#### E. 回放与导出

- 可回放当前 attempt，允许带少量上下文试听，但回放时不改变采集索引。
- 按选中 attempt 导出单句 WAV，可配置前后 padding；所有边界都在整数样本上计算。
- 导出 `metadata.csv`、`metadata.json` 和 `manifest.json`，包含参数、条目状态、选中 attempt、时长、源分段与文件名。
- 导出前检查 ID 唯一、边界有效、文件可读、音频格式一致和磁盘空间。
- 跳过项和无有效 attempt 项不默默忽略，必须在导出报告中明确列出。

### 4.2 P1：MVP 稳定后增加

- 全键盘工作流和可自定义快捷键。
- 全局任务搜索、按 ID 跳转、驳回标签、批量选择 attempt。
- 波形缩放和边界微调，支持按样本或毫秒调整导出范围。
- 设备热插拔恢复向导、磁盘空间趋势预警、输入过小/持续削波告警。
- 本地质检：静音过长、时长越界、峰值过高/过低、空音频和基础格式检查。
- Excel 导入导出、TextGrid 导出、文件校验和可配置命名模板。
- 长录音打点模式。

### 4.3 P2：平台化能力

- 接入现有 DataBaker 账号、任务领取和团队权限。
- 按现有 OSS 规则上传，支持断点、重试队列和服务端提交状态。
- 声纹测试任务、服务端机检、驳回重录和审核闭环。
- 审计日志、中央配置、版本更新和运行状态上报。

## 5. 交互方案

### 5.1 页面结构

#### 首页 / Session 管理

- 最近 Session：进度、最后编辑时间、设备、异常关闭标记。
- “新建 Session”向导：选脚本 → 预览与校验 → 选设备/格式 → 预检 → 开始。
- 不直接在首页放置大量高级参数；常用配置使用预设。

#### 录制工作台

- **左栏**：句子目录、筛选和快速定位。状态使用颜色 + 图标 + 文字，不仅依赖颜色。
- **中间主区**：当前编号、朗读要求标签、大字号文本、attempt 状态、波形/电平和主操作。
- **右栏**：输入设备、音频参数、Session 状态、存储空间、告警和当前 attempt 列表。
- **顶部状态条**：项目名、已完成/总数、持续录制时长、自动保存状态。
- **底部操作条**：试听、上一条、开始/结束 attempt、确认并下一条、重录、跳过。

建议提供“专注模式”：隐藏左右栏，仅保留大文本、状态、电平和底部操作，适合实际朗读。

### 5.2 快捷键默认方案

| 按键 | 非录制状态 | 录制中 | 录后待确认 |
| --- | --- | --- | --- |
| `Space` | 开始 attempt | 结束 attempt | 确认并下一条 |
| `R` | 对当前句开始重录 | 无动作 | 重录 |
| `P` | 试听有效 attempt | 无动作 | 试听/暂停 |
| `S` | 跳过当前句 | 无动作 | 跳过 |
| `←` / `→` | 上一/下一可访问条目 | 禁止 | 上一/下一可访问条目 |
| `Esc` | 暂停 Session | 先结束当前 attempt，再暂停 | 暂停 Session |
| `Ctrl+S` | 立即 checkpoint | 立即 checkpoint | 立即 checkpoint |

按键义与随状态变化时，主按钮和帮助区必须同步显示当前操作，不依赖用户记忆。

### 5.3 状态机

```text
NEW
 → PREFLIGHT
 → READY
 → CAPTURING_SESSION
     → ITEM_READY
     → ATTEMPT_RECORDING
     → ATTEMPT_CLOSING
     → ATTEMPT_REVIEW
         ├─→ ACCEPTED → ITEM_READY(next)
         ├─→ RETAKE   → ATTEMPT_RECORDING
         └─→ SKIPPED  → ITEM_READY(next)
 → PAUSED
 → COMPLETED
 → EXPORTING
 → EXPORTED

任意活动状态 → FAULT → RECOVERY_CHECK → PAUSED/SEALED
```

关键规则：

- `ATTEMPT_CLOSING` 完成之前不允许切换文本或立即退出。
- 录音时不允许更换设备、采样率、位深或声道。
- 进入 `FAULT` 后必须先停止产生“有效 attempt”标记，不得带故障继续。
- 正常会话中音频时轴可持续存在，但只有 `ATTEMPT_RECORDING` 区间和导出 padding 会进入最终单句文件。

## 6. 数据与文件设计

### 6.1 Session 目录

```text
Recordings/
└── <session_id>/
    ├── session.json
    ├── script/
    │   ├── source.tsv
    │   └── normalized.json
    ├── audio/
    │   ├── master_0001.wav
    │   ├── master_0002.wav
    │   └── segments.json
    ├── metadata/
    │   ├── events.jsonl
    │   ├── items.snapshot.json
    │   └── recovery.json
    ├── logs/
    │   └── app.log
    └── export/
```

`master_0001.wav` 等在逻辑上是一条连续时轴。每个分段在 `segments.json` 中记录 `global_start_sample`、样本数、文件大小和结束状态。建议按时长或文件大小轮换，避免单个 WAV 过大或因异常关闭损坏全部会话。如交付必须需要一个物理 master，可在导出阶段无损合并或生成 RF64/BWF。

### 6.2 核心对象

```json
{
  "schema_version": 1,
  "session_id": "20260810-roomA-speaker001",
  "audio_format": {
    "sample_rate": 48000,
    "bit_depth": 24,
    "channels": 1
  },
  "items": [
    {
      "id": "000023",
      "text": "今天天气非常适合出去散步。",
      "labels": ["normal"],
      "status": "accepted",
      "attempts": [
        {
          "attempt_id": "a1",
          "start_sample": 6491568,
          "end_sample": 6648576,
          "status": "rejected_by_operator",
          "segment_refs": ["master_0001.wav"]
        },
        {
          "attempt_id": "a2",
          "start_sample": 6820944,
          "end_sample": 6970176,
          "status": "accepted",
          "segment_refs": ["master_0001.wav"]
        }
      ],
      "selected_attempt_id": "a2"
    }
  ]
}
```

要求：

- `start_sample` 包含，`end_sample` 不包含，区间表示为 `[start_sample, end_sample)`。
- 音频格式在一个 Session 内不可变；如必须变更，新建 Session。
- attempt 创建后不改写边界；人工边界调整创建一条修订记录，或保留原始边界和导出边界两组字段。
- `items.snapshot.json` 是便于加载的派生快照，`events.jsonl` 是审计和恢复根据。
- 文本和音频可能属于敏感数据；日志默认不记录全量文本、音频内容或账号凭证。

## 7. 技术方案

### 7.1 推荐技术栈

已确认的 MVP 技术栈：

- **Electron**：桌面容器、单实例、窗口、文件选择、应用生命周期和 Rust 子进程管理。
- **React + TypeScript**：Session 向导、录制工作台、任务目录、设备预检、状态投影和快捷键。
- **Rust sidecar**：独立的 `recorder-engine` 可执行文件，负责设备枚举、参数协商、PCM 采集、样本计数、分段写盘、Session/attempt 状态机、日志、恢复和导出。
- **Windows 音频后端适配层**：首版以 WASAPI 为默认目标；可从跨平台音频库或 Win32 直接实现中择一，但上层只依赖 `AudioBackend` trait。
- **PCM 文件写入层**：支持 WAV 和必要时的 RF64/BWF；不让格式库的具体 API 渗透到 Session 领域模型。
- **JSONL + 原子 JSON 快照**：Rust 引擎的权威恢复数据。SQLite 可作为搜索加速层，但不是唯一可恢复来源。

不建议首版把 Rust 做成 Node 原生扩展。独立 sidecar 可以避免 Electron/Node ABI 绑定，并允许 Electron 渲染进程崩溃后音频引擎安全停止、封闭文件和写入恢复状态。C++ 仅在 ASIO、设备厂商 SDK 或 Rust 音频后端无法覆盖的能力上作为窄适配层，不和 Electron 渲染进程直接耦合。

### 7.2 模块边界

```text
Electron renderer (React)
 ├── Session / Script / Device / Recorder views
 ├── ViewModels + state projection
 └── 不启用 Node 直接访问
             │ 窄 preload bridge
Electron main process
 ├── 窗口、文件对话框、单实例
 ├── recorder-engine 启动/监控/退出
 └── IPC 校验、请求关联和协议版本握手
             │ NDJSON over stdio（MVP）
Rust recorder-engine
 ├── Application: Session / Recording / Recovery / Export
 ├── Domain: Session / Item / Attempt / State machine
 └── Infrastructure
     ├── AudioBackend (WASAPI adapter)
     ├── AudioWriter (WAV/RF64 adapter)
     ├── EventJournal / Snapshot / optional SQLite
     ├── Exporter
     └── Diagnostics
```

不把 OSS、服务端机检或具体 UI 控件写进核心录音引擎；后续平台接入作为 Electron main 或 Rust 中的独立 Adapter。渲染进程只能通过预加载脚本暴露的白名单 API 发送已校验命令，不直接启动进程、读写任意路径或获取原始 PCM。

### 7.3 IPC 协议

MVP 使用每行一个 JSON 对象的双向协议。命令必须包含 `protocol_version`、`request_id`、`command`、`payload`；响应和异步事件必须包含引擎状态序号。

```json
{"protocol_version":1,"request_id":"r-104","command":"stop_attempt","payload":{"item_id":"000023"}}
{"protocol_version":1,"request_id":"r-104","ok":true,"result":{"attempt_id":"a2","start_sample":6820944,"end_sample":6970176}}
```

通过 IPC 传输的是命令、样本位置、状态、错误和降采样电平，不是全量 PCM。引擎事件流建议限制在 15–30 Hz。Electron 主进程必须在启动时校验协议版本；不兼容时禁止开始录音，而不是尝试降级运行。

### 7.4 Rust 引擎线程与数据流

```text
Audio callback
  ├── 维护单调 captured_sample_cursor
  └── 只复制音频块、记录 callback 状态、推入有界队列
             │
Writer thread
  ├── 持续写音频分段
  ├── 更新 committed_sample_count
  └── 轮换/封闭分段，上报写盘错误
             │
Workflow thread / event loop
  ├── 根据 captured cursor 的原子快照创建 attempt 边界
  ├── 结束 attempt 后等待 committed cursor 追上 end_sample
  ├── 追加事件日志和原子快照
  └── 将业务状态投影给 UI
             │
Telemetry publisher
  ├── 15–30 Hz 生成降采样电平/波形事件
  └── 通过 IPC 发送状态，不发送原始全量 PCM
```

有界队列绝不得在溢出时静默丢块。一旦发生 overflow/underflow，必须记录具体样本范围并进入故障流程，不将受影响的 attempt 标记为合格。

### 7.5 静音和句间间隔

建议将三个概念分开：

1. **操作节奏**：文本展示后是否倒计时，确认后多久显示下一句。
2. **录音标记边界**：操作员或 VAD 确定的原始 attempt 起止样本。V1 以人工标记为主。
3. **导出 padding**：在原始边界前后额外保留的样本数，且必须限制在 Session 有效范围内。

这样可以避免为了导出 100 ms 静音，在采集环节强制用户每句等待 1–3 秒，也避免连续时轴上的句间静音被重复计入两句。

## 8. 开发计划

以 1 名熟悉 React/Electron、Rust 和音频 I/O 的开发为例，MVP 预估为 **7–10 人周**。如开发者需要同时学习 Rust 或实时音频，应按 10–14 人周规划。如要同期接入现有后端、OSS 和服务端机检，再额外预留 2–4 人周且受接口联调影响。

### 阶段 0：决策收敛与技术尖刺（1 周）

- 确认第 11 节中的阻塞项。
- 使用目标 USB 麦克风/声卡验证设备枚举、参数协商、16/24-bit、单/双声道和热插拔。
- 完成 Rust 最小录音引擎，连续录制 2 小时，记录 callback 间隔、队列深度、写盘耗时和丢帧。
- 完成 Electron main 启动 sidecar、协议握手、命令/事件往返和引擎崩溃监测。
- 强制结束进程，验证分段封闭和恢复策略。
- 产出：技术选型结论、基准数据和 Go/No-Go 决策。

### 阶段 1：Rust 核心录音引擎（2–3 周）

- AudioEngine 接口、设备适配、有界缓冲队列、Writer 线程和分段轮换。
- 全局样本计数、分段映射、峰值/RMS 统计和故障上报。
- 纯引擎测试：样本数、分段连续性、格式和超时停止。

### 阶段 2：Electron/React 应用与作业 UI（1.5–2 周）

- Electron 主进程、preload 白名单 API、React 状态投影和 sidecar 生命周期。
- Session 向导、脚本导入/预览、设备预检。
- 三栏录制工作台、进度、大文本卡、电平/波形和状态机。
- 确认、重录、跳过、返回复核和基础快捷键。

### 阶段 3：持久化、恢复与导出（1.5–2 周）

- 事件日志、原子快照、Session 完整性检查和恢复向导。
- 单句 WAV 切分、CSV/JSON/manifest 导出、导出报告。
- 单元测试：跨 master 分段切分、padding 裁切、多 attempt 选择、跳过项、非法边界。

### 阶段 4：集成、打包和系统测试（1–2 周）

- 使用至少 3 类设备和 2 台 Windows 机器完成长时间测试。

- 将对应 CPU 架构的 `recorder-engine` 随 Electron 安装包分发，校验路径、权限、签名和协议版本。
- 打包、安装/卸载、版本和诊断包导出。
- 小规模真实作业试点，根据操作次数和失误点优化 UX。

## 9. 验收标准

### 9.1 功能验收

- 可导入含 500 条文本的合法 TSV/CSV，并对错误行给出可定位的提示。
- 可在同一 Session 完成录制、重录、跳过、回放和选择有效 attempt。
- 程序重启后可恢复到最近一次 checkpoint，已确认条目不丢失。
- 导出单句 WAV 数量、文件名、采样格式和元数据一致，报告中可见跳过/失败项。

### 9.2 音频与稳定性验收

- 目标设备连续录制 2 小时，应用无崩溃、无队列溢出和未解释的 callback 状态。
- 导出音频总样本数与元数据边界一致，时长偏差不超过 1 个样本。
- 两个物理 master 分段之间的逻辑样本位置连续，跨段 attempt 可正确导出。
- 设备拔出或写盘失败后应用在 1 秒内给出不可忽略的故障提示，且不将受影响 attempt 标记为合格。

### 9.3 UX 验收

- 熟练用户可仅使用键盘完成一组脚本的录制、重录和跳过。
- 用户始终能回答：当前是否在录、录的是哪句、数据是否已保存、发生失败后数据是否仍在。
- 主操作不应因为用户快速连续点击而生成重叠 attempt、空边界或并发写盘任务。

## 10. 主要风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| Electron 渲染进程卡顿或崩溃 | UI 中断、重复命令 | Rust 引擎独立持续写盘；命令幂等；引擎发送权威状态序号；重启 UI 后重建投影 |
| Rust 音频 callback 做过多工作 | 丢帧、断裂 | callback 最小化、有界队列、Writer 独立、长录基准；绝不在 callback 中做 IPC/写盘/序列化 |
| Electron 与 Rust 协议版本不匹配 | 命令语义错乱、数据损坏 | 启动握手、明确协议版本、不兼容时禁止录音、联合集成测试 |
| 某些声卡宣称支持的格式与实际不一致 | 无法开始或被静默转码 | 真机参数协商、录前短录回读、保存实际格式 |
| 单文件过大或异常退出破坏 WAV 头 | 大量数据丢失 | 逻辑连续 + 物理分段、及时封闭、恢复扫描、必要时 RF64/BWF |
| 文本导入后被外部修改 | ID/音频错配 | Session 内保存脚本快照和哈希 |
| 超长 Session 导致内存中保留全量波形 | 内存上升、UI 越来越慢 | 只保留实时窗口，长时间概览使用分层峰值缓存 |
| 过早接入移动端全部平台能力 | MVP 范围膨胀 | 先固化本地数据协议和录音稳定性，平台接入作为 P2 Adapter |
| 音频和脚本涉及敏感信息 | 隐私和交付风险 | 最小日志、权限受控路径、可配置加密/保留期、不将凭证写入项目文件 |

## 11. 开发前必须确认的产品决策

以下 6 项会实质影响架构或 MVP 边界，建议在阶段 0 锁定：

1. **是否接入现有平台**：首版是纯本地工具，还是必须登录、获取任务、上传并接受机检？
2. **交付音频规范**：采样率、位深、声道是项目强制、管理员预设，还是允许采集员自由选择？
3. **master 的交付形式**：业务真正要求一个物理 WAV，还是只要一条逻辑连续时轴？
4. **逐句边界如何产生**：首版是人工按键开始/结束，还是要求语音活动检测自动分段？建议 V1 手动，VAD 仅做提示。
5. **支持环境**：Windows 10/11 的最低版本、常用声卡型号、是否需要 ASIO，以及最长单次 Session 是多久？
6. **完成规则**：是由采集员确认即完成，还是必须通过本地检测或服务端质检才能进入下一条？

如尚未能决定，建议 MVP 使用的默认是：**Electron + React + TypeScript 界面、Rust sidecar 录音引擎、纯本地、任务参数固定、逻辑连续但物理分段、手动边界、Windows 10/11 + WASAPI、人工确认即完成**。这组默认能最快验证桌面作业效率和连续录音架构。
